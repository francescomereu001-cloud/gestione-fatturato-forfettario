## Actual Aruba workbook and confirmed business policy

The supplied `20261007_ReportFattureInviate.xls` is a binary XLS with sheet FattureInviate, 26 columns and 18 documents, including 3 credit notes. Its headers differ from the initially described custom report: Numero, Nome file, ID SdI, Data documento, Tipo documento, Cliente, Totale documento, Netto a pagare, Incassi, Data incasso, Stato, and tax/transport columns. It contains **no ENASARCO column**. Explicit types are `Fattura - TD01` and `Nota di credito - TD04`; credit amounts are already negative. Customer/tax IDs and financial amounts from the upload are never committed as fixtures.

`aruba_invoice_report_v1` has two deterministic header profiles: the actual portal export above, and the explicitly described seven-column report N. fattura / Società / Data fattura / Descrizione del progetto / Totale fattura / ENASARCO / Netto a pagare (ENASARCO). Header comparisons allow case, accents and whitespace only. No substring/fuzzy guessing. Explicit documentary ENASARCO takes precedence. **The user confirmed that the entire difference between gross and net payable is exclusively ENASARCO**: when the column is absent, derive gross minus net, and record `document_gross_net_delta` in normalized audit data and invoice import_metadata. The server recomputes that difference rather than trusting a claimed withholding. Neither original gross nor net is changed. Unknown withholding from an unsupported/malformed payload remains null and incomplete, never invented as zero.

FinancialMind treats every valid issued invoice as collected on its document date. New RPC writes persist incassata=true/data_incasso=data; historical stored flags/dates remain unchanged, and the read projection applies the policy. Bank deposits affect liquidity/cashflow, never add a second invoice income. Legitimate zero and negative values are retained. Mismatch over two cents is a warning and never silently corrected. Explicit TD04 normalizes positive magnitudes to negative economic values; already-negative values stay negative. Raw cells remain in audit. Negative documents without an explicit credit type remain signed adjustments with a verification warning. Positive credits without explicit type evidence cannot be identified from a description alone.

## Staging, identity, conflicts and security

Additive migration `20261007222751_pr12_income_taxes_v2.sql` was created with Supabase CLI. New invoice metadata: document_type, source_document_id, source, parser_key, import_batch_id, source_fingerprint, imported_at, import_metadata. Existing columns and rows are untouched. `invoice_import_batches` and `invoice_import_rows` retain file/source/parser, raw/normalized cells, server-computed identity/fingerprint, statuses, warnings and final counts. Composite owner-aware FKs protect batch/invoice links.

`stage_invoice_import_batch` persists preview without invoice writes. `commit_invoice_import_batch` re-evaluates against current invoices and commits all permitted inserts/audit/counts in one transaction. Batch retries are idempotent. Owner advisory locks serialize commits, including direct invoice mutations via a lock-only trigger. Client owner/flags/warnings/counts are not authorization or numerical authority. Input is limited to 10,000 rows, finite cent values, valid dates, bounded number/customer/description/ID lengths and allowlisted types.

Identity prioritizes ID SdI when available; fallback is owner + normalized document number + document year + type. Date, customer, gross, ENASARCO, net and description are compared as payload, so changes become conflicts rather than creating income again. Legacy rows are matched without rewriting them. Multiple legacy matches are ambiguous conflicts. The fingerprint is computed server-side with md5 of canonical JSON (identity/dedup helper, not a cryptographic authenticity proof).

Statuses: `new` → `inserted`; `existing_unchanged` = matching existing values; `exact_duplicate` = identical identity/content repeated within the report; `conflict` = changed payload or ambiguous identity; `rejected` = invalid normalized row. Cumulative imports insert only new documents. Conflicts remain visible and are excluded from insert; existing financial amounts are preserved. **There is no update/delete/import-conflict replacement RPC in PR12**: updated_count is explicitly zero. Correcting an existing document requires a separately reviewed audited correction workflow; it is not silently offered by this import. This conservative scope protects legacy fiscal records.

Public RPCs are SECURITY INVOKER with empty search_path. Audit tables grant authenticated SELECT only and owner RLS, with anon/PUBLIC revoked. The sole audit writer is SECURITY DEFINER in unexposed financial_private, owned by postgres, explicitly checking auth.uid() and owner on every path. This is necessary to keep audit rows/counts immutable to direct client writes. Direct SQL calls to this private function retain identical ownership checks. Never expose financial_private through the Data API. No frontend service-role credential.
